# Acceso a Google Drive del lado del servidor, para publicar sin el picker abierto

El notebook de Ideas (ver ADR-0013) tiene que poder publicar solo, a la hora programada, sin que Bautista tenga el navegador abierto en ese momento — a diferencia de `/publicar`, donde el archivo siempre se elige ahí mismo con el Picker interactivo de Google (token OAuth de ~1h, scope `drive.readonly`, ver ADR-0009).

Primera opción evaluada: reusar el mismo Picker interactivo también para calendarizar una Idea — "programar" abriría el picker, se elegiría el archivo ahí, y se prepararía (baja de Drive, sube a Storage) en el momento, igual que hoy. Simple, cero infraestructura nueva. El propio Bautista encontró el problema real: su forma de trabajar es calendarizar de una sentada bastante contenido por adelantado (del orden de ~30 archivos × 4 Cuentas para armar un mes junto) — con esa opción, todos esos archivos ya convertidos quedarían guardados en Supabase Storage desde el momento de programar hasta su fecha real, semanas después. Con fotos son pocos MB cada una, pero con reels/video el acumulado puede llegar a varios GB en simultáneo, en un VPS compartido con otros proyectos (ver ADR-0002/0003) — exactamente lo que ADR-0009 ya aceptaba como costo menor para el caso ocasional, pero no para este volumen.

Decisión: agregar un OAuth "offline" de Google (consentimiento único, pantalla `/configuracion`, sólo para el dueño del panel — es un recurso global, no por Cuenta de Instagram), que guarda un refresh token cifrado en la base (`DriveCredencial`, mismo cifrado AES-256-GCM que ya usa `lib/crypto/token-cipher.ts` para el token de Meta, ver ADR-0007). Con ese refresh token el servidor puede pedir un access token de Drive fresco en cualquier momento futuro, sin depender de una sesión de navegador activa — lo que permite bajar el archivo recién cerca de su hora programada (ver ADR-0015) en vez de al calendarizar, manteniendo el uso de Storage acotado a minutos por Publicación en vez de semanas, sin importar cuánto se planifique por adelantado.

A diferencia del token de Meta, que expira (~60 días) y necesita un worker de renovación proactiva (`lib/worker/token-renewal-worker.ts`, ver ticket 07), el refresh token de Google no vence en un plazo fijo — se usa bajo demanda, minteando un access token nuevo en cada uso. No hace falta un worker de renovación aparte; si Google lo revoca, el error queda en la Publicación afectada apuntando a `/configuracion`.
